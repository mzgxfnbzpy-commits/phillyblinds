Cart, Checkout & Order-Review System

Universal cart architecture for Philly Blinds & Blindznation. One cart, one saved contact, one bundled order across every product line — roller, cellular, roman, drapery, shutters, blinds.

Vanilla JS · no framework Engine: js/shared.js Backend: api/quote.js (Vercel + Resend) Storage: localStorage

1System Overview

The cart is one shared engine loaded on every page via js/shared.js. Each product configurator only has to hand the engine a normalized item; the engine owns storage, the drawer UI, contact persistence, checkout, and the email handoff.

Product configurator → pbAddToCart(item) → localStorage pb_cart_v1 → Cart drawer → pbGoCheckout() → Quote modal → POST /api/quote → Resend → team + customer email

Two persistence layers

pb_cart_v1 — the array of configured products (the "basket").
pb_contact_v1 — name / email / phone, entered once and reused on every product page and at checkout.

Two submit paths, one button text

Add to Cart — saves config silently, no contact required.
Submit Order for Review — requires name + email + phone, bundles the whole cart, fires the email. No payment is taken.

Dual-site rule
Everything in this document is identical on phillyblinds and blindznation. Only swap brand-specific values: team email addresses, BRAND/SITE_URL in api/quote.js, the mailto fallback address, and the CSS color tokens. The cart logic, schemas, and validation are byte-for-byte the same.

2The Two Buttons (every product page)

Every configurator renders its estimate/CTA block through pbRenderEstimate() in shared.js. That block is where the two buttons live, so adding them to a new product page is automatic once the page calls that function.

Naming — action required
The cart drawer's checkout button already reads "Submit Order for Review →" (shared.js _initCart()). The per-product panel button currently reads "Get My Free Estimate →" (pbRenderEstimate()). Per the payment-flow spec the per-product button should also read "Submit Order for Review". This is a one-line label change — see Build Checklist item 3.

Drop-in markup for a new product page

A configurator only needs to call pbRenderEstimate() after each price calc. The engine injects both buttons, the line-item summary, and the estimate disclaimer:

3Cart Architecture

All cart code lives in js/shared.js, loaded on every page. No per-page cart code is needed. Functions are grouped into five concerns.

ConcernKey functionsWhat it does
Contact persistence pbGetContact() · pbSaveContact() · pbAutoFillContact() · pbContactValid() Reads/writes pb_contact_v1; auto-fills any [data-pb-contact] input and rebinds a save-on-input listener on every page load.
Cart engine pbGetCart() · pbAddToCart() · pbRemoveCartItem() · pbClearCart() · _pbSaveCart() CRUD over the pb_cart_v1 array. Each item gets a unique cartId. Save triggers badge + toast.
Drawer UI pbOpenCart() · pbCloseCart() · _renderCartBody() · _initCart() · _updateCartBadge() Injects the slide-out drawer + overlay + toast into <body> once. Renders line items, per-item + running estimate, remove buttons.
Estimate / CTA panel pbRenderEstimate() · pbEstimateAddCart() · pbOpenQuoteFromPanel() · pbCollectItem() Renders the per-product configuration summary + the two buttons. Bridges a configurator's selection into a cart item.
Checkout / quote pbGoCheckout() · pbShowQuoteModal() · pbSubmitQuote() Flattens the whole cart into one selection list, opens the contact modal, POSTs to /api/quote, renders success / mailto-fallback.
Motorization sub-modal pbAddToCartWithMotor() · _pmmConfirm() · normanMotorSection() Optional motor-options overlay for motorizable products; result stored on the item as motorized + motorOptions.

Why a single shared engine

  • One basket across product types. A roller shade, a roman, and a set of shutters all land in the same pb_cart_v1 array and submit together.
  • Contact entered once. pb_contact_v1 is read by every product page's contact fields and by the checkout modal — the customer never re-types name/email/phone.
  • Add a product = call one function. New configurators inherit cart, drawer, checkout, validation, and email for free.

Two JSON values in localStorage. Versioned keys (_v1) so the schema can be migrated without colliding with old data.

4.2 — Contact schema

Written by pbSaveContact(); read by pbAutoFillContact() and pre-filled into the checkout modal. address is optional / proposed per spec:

localStorage['pb_contact_v1'] = {
  name:    "Jane Smith",      // full name (modal splits into first/last)
  email:   "jane@example.com",
  phone:   "(215) 555-0100",
  address: "123 Main St, Huntingdon Valley PA"  // NEW — optional, proposed
}
How contact auto-fill works
Any input on any page tagged data-pb-contact="name|email|phone|address" is auto-populated from pb_contact_v1 on load, and re-saves on every keystroke. That is the entire "enter once, carry everywhere" mechanism — a configurator just needs to add the attribute to its contact inputs.

5LocalStorage / Session Handling

5.1 — Keys & access functions

KeyTypeReadWriteLifetime
pb_cart_v1JSON arraypbGetCart()_pbSaveCart()Persistent (until checkout/clear)
pb_contact_v1JSON objectpbGetContact()pbSaveContact()Persistent (reused indefinitely)

Every read is wrapped in try/catch and falls back to [] / {}, so corrupt or absent storage never throws. Writes are also guarded (private-mode / quota errors fail silently).

5.2 — Why localStorage, not sessionStorage

The cart and contact must survive page navigation between product pages and across browser sessions (a customer configuring shades over several days). sessionStorage would drop the cart on tab close. localStorage is the correct choice; there is no server-side cart — the basket is entirely client-side until the order is submitted.

⚠ Critical constraint — attachments & the 5 MB quota

localStorage is capped at ~5 MB per origin and only stores strings. Storing uploaded photos/PDFs as base64 inside pb_cart_v1 will overflow that quota after just 2–3 phone photos (base64 inflates size ~33%, and a single iPhone photo is 3–5 MB). When the quota is hit, setItem throws and — because writes are silently caught — the cart save fails without warning.

Recommended handling for files (pick one):

  1. Defer upload to checkout (simplest). Keep only file metadata (name/type/size) in the cart for display; attach the actual File objects only at submit time via FormData to /api/quote. Files never enter localStorage. ← recommended.
  2. IndexedDB for blobs. Store File/Blob objects in IndexedDB keyed by cartId (no 5 MB string cap, holds binary natively); keep only the metadata reference in pb_cart_v1.
  3. Direct-to-storage. Upload on selection to Vercel Blob / S3, store only the returned URL in the cart item. Best for large files but adds infra.

5.3 — Recommended file handling (option 1, no infra)

// At Add-to-Cart: keep lightweight metadata only (safe for localStorage)
item.attachments = Array.from(fileInput.files).map(f => ({
  name: f.name, type: f.type, size: f.size
}));
// Hold the real File objects in memory keyed by cartId (not serialized):
window._pbFiles = window._pbFiles || {};
window._pbFiles[item.cartId] = Array.from(fileInput.files);

// At checkout: send as multipart so binaries never touch localStorage or JSON
const fd = new FormData();
fd.append('payload', JSON.stringify(orderPayload));
Object.values(window._pbFiles).flat().forEach(f => fd.append('attachments', f));
fetch('/api/quote', { method:'POST', body: fd });

Trade-off: in-memory files are lost on hard page reload (metadata still shows in the cart so the customer can re-attach). For cross-reload durability use option 2 (IndexedDB).

6Email Payload Structure

Checkout POSTs to the Vercel serverless function api/quote.js, which sends two emails through Resend: one to the team and one confirmation to the customer.

6.1 — Current request contract (JSON)

POST /api/quote · Content-Type: application/json — built in pbSubmitQuote():

{
  name:       "Jane Smith",          // required
  email:      "jane@example.com",    // required, regex-validated
  phone:      "(215) 555-0100",
  product:    "3 items",             // or single product name
  selections: [ {label, value}, ... ],  // whole cart flattened; max 60 rows server-side
  estimate:   "$1,240 (estimate only)",  // or null
  notes:      "...",
  sourceUrl:  "https://www.phillyblinds.com/pages/shades.html",
  _hp:        "",                    // honeypot — must stay empty
  _t:         8423                    // ms since form load (anti-bot timing)
}

6.2 — How the cart maps into the payload

pbGoCheckout() flattens every cart item into the selections array, inserting a divider row per item and expanding lines / motorization / per-item estimate:

selections = [
  { label:"─── Item 1", value:"Norman Soluna Roller Shade" },
  { label:"Width",      value:"36 in" },
  { label:"Estimate",   value:"$312 (estimate only)" },
  { label:"─── Item 2", value:"Custom Roman Shade" },
  { label:"Price",      value:"Custom quote" },
  ...
]

6.3 — Response & server actions

OutcomeHTTPBodyClient behavior
Success200{ ok: true }Show success state; pbSaveContact(); (clear cart — see checklist)
Bot / honeypot / too-fast200{ ok: true }Silent accept, no email sent
Validation400{ error }Show inline error
Rate limited429{ error }Show "wait a few minutes"
Email key missing503{ error }Fall back to mailto link
Send failed500{ error, fallback }Render mailto + phone fallback

On success the server sends: (a) a styled team email to justin / sarah / mike / tarin @phillyblinds.com with the full configuration table and reply_to set to the customer, and (b) a branded confirmation to the customer (only if their email is valid). Env vars required in Vercel: RESEND_API_KEY (and optional RESEND_FROM).

6.4 — Proposed: attachments + address NEW

To carry files and the optional address through, switch the request to multipart/form-data and extend the server to forward Resend attachments:

// CLIENT — multipart instead of JSON
fd.append('payload', JSON.stringify({ ...order, address }));
files.forEach(f => fd.append('attachments', f));

// SERVER (api/quote.js) — Resend supports base64 attachments:
attachments: files.map(f => ({ filename: f.name, content: f.base64 }))
Server note
The current api/quote.js has a 20 KB body guard and parses JSON only. Multipart + attachments needs: raised body limit, a multipart parser (or Vercel's built-in), and a per-file size/type allow-list mirroring the client (image/* , .pdf, .heic). Keep total attachment size within Resend's 40 MB message cap.

7Validation Requirements

Validation runs in two places: the browser (UX + fast feedback) and the server (authoritative + anti-abuse). Add to Cart requires nothing; Submit Order for Review requires name + email + phone.

7.1 — Client-side (shared.js)

EmailNon-empty + /^[^\s@]+@[^\s@]+\.[^\s@]+$/pbContactValid(), pbSubmitQuote()
PhoneRequired for Submit Order (per spec)pbContactValid() modal: make required
AddressOptional—
Config conflictNon-empty conflictMsg disables submitpbRenderEstimate()
Filesaccept="image/*,.pdf,.heic,.png,.jpg,.jpeg"file input + (add size cap, see §5.2)
Spec gap — phone
Terminal 2 requires phone for Submit Order. pbContactValid() already enforces name + phone + email, but the standalone checkout modal (pbSubmitQuote()) validates only name + email and treats phone as preferred-but-optional. Make phone required in the modal to fully match the spec.

Design principle
The client validates for UX; the server never trusts the client. Every field is length-capped and HTML-escaped server-side before being interpolated into the email template, and silent 200s on bot signals avoid teaching scrapers what tripped them.
